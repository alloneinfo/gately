# Gately v0.6.0 est disponible

27 octobre 2026

Cette version exécute plusieurs instances frp, et le Service web gagne le routage par utilisateur ([#29](https://github.com/wangwanjie/gately/issues/29)), les groupes et le tri des sites ([#28](https://github.com/wangwanjie/gately/issues/28)) ainsi que la transmission des cookies de connexion ([#30](https://github.com/wangwanjie/gately/issues/30)). Elle corrige aussi les certificats des sous-domaines hébergés chez un autre fournisseur DNS ([#27](https://github.com/wangwanjie/gately/issues/27)).

[Télécharger v0.6.0](/fr/download) · [GitHub Release](https://github.com/wangwanjie/gately/releases/tag/v0.6.0)

## Plusieurs instances frp

- Exécutez plusieurs instances frpc (chacune reliée à un frps) et plusieurs instances frps (chacune sur ses propres ports). Chaque instance est un processus distinct avec son propre fichier de configuration et sa propre source de journaux, et peut être activée, redémarrée, modifiée et supprimée séparément ;
- les proxys appartiennent à une instance frpc et la liste peut être filtrée par instance ; modifier un proxy ne redémarre que les instances dont la configuration a changé ; supprimer une instance frpc supprime ses proxys ;
- les chemins des programmes passent dans une carte Programmes séparée ;
- les imports ini / toml peuvent viser une instance existante ou une nouvelle, et l'import Lucky reprend toutes les instances frpc / frps ;
- les anciens réglages frpc / frps uniques sont migrés lors de la mise à jour vers des instances nommées frpc / frps, en conservant le jeton et les proxys.

Voir [Réseaux et tunnels](/fr/docs/modules/tunnels).

## Service web

- **Routage par utilisateur connecté** : les sites en proxy inverse avec authentification basique, web ou déléguée peuvent envoyer les utilisateurs listés vers leurs propres backends, comme `map $remote_user $backend` de nginx. Les utilisateurs peuvent être des utilisateurs du site, des utilisateurs partagés, `fournisseur:id` pour la connexion tierce, ou le `Remote-User` renvoyé par l'authentification déléguée ; les utilisateurs non listés et les visiteurs non connectés sur les chemins publics utilisent les backends du site. Un en-tête comme `X-Remote-User` peut transmettre le nom d'utilisateur au backend, et le même en-tête envoyé par les visiteurs (y compris avec des tirets bas à la place des traits d'union) est toujours supprimé.
- **Groupes, tri et recherche des sites** : les sites peuvent avoir un groupe et s'affichent en groupes repliables sous chaque écouteur ; le mode Tri déplace les sites vers le haut ou le bas ou par glisser-déposer, déplace des groupes entiers et réordonne les écouteurs ; le champ de recherche filtre par domaine, nom, groupe, backend et remarque. L'ordre agit uniquement sur la liste ; la correspondance des domaines en est indépendante.
- **Transmettre les cookies de connexion Gately** : une nouvelle option de proxy inverse qui transmet tels quels au backend les cookies d'authentification unique et de session du site. Un Gately public peut ainsi assurer seulement le WAF et le contrôle d'accès devant un Gately du réseau local qui gère l'authentification web et l'authentification unique. L'option est incompatible avec une authentification sur le même site.

Voir [Services Web](/fr/docs/modules/web).

## Certificats

Quand la zone est laissée vide, la validation DNS-01 recherche d'abord la zone faisant autorité pour l'enregistrement de validation avec une requête SOA, de sorte que les sous-domaines hébergés chez un autre fournisseur DNS (web.example.com séparé de example.com) et les suffixes à plusieurs niveaux sont correctement détectés. Si la recherche échoue, ou renvoie une zone plus courte que le domaine enregistrable (par exemple quand un DNS local remplace un domaine parent), la zone est déduite du nom de domaine et la raison est journalisée. Les serveurs DNS définis sur un certificat s'appliquent désormais à ce seul certificat.

## Afficher les mots de passe enregistrés

Les mots de passe, jetons et clés masqués ont un bouton en forme d'œil qui récupère le texte en clair via les nouveaux points d'accès `.../secrets` :

- le droit d'écriture est requis : les comptes en lecture seule et les jetons API en lecture seule reçoivent 403, et chaque consultation est inscrite dans le journal d'audit ;
- les mots de passe des connexions et des préréglages d'authentification du terminal web exigent d'abord la vérification à deux facteurs du terminal, comme à l'ouverture d'un terminal ;
- les mots de passe des utilisateurs web hachés avec bcrypt, les secrets client OIDC et les clés privées ne sont jamais renvoyés ;
- les utilisateurs partagés avec connexion à deux facteurs peuvent afficher à nouveau leur QR code ;
- le mode lecture seule par défaut de `gately mcp` n'expose pas ces points d'accès ; ils sont disponibles avec `--write`.

## Notes de mise à jour

- Comment mettre à jour : les installations par binaire Linux se mettent à jour depuis la page À propos ; avec Docker, récupérez la nouvelle image et recréez le conteneur ; sur fnOS, installez le nouveau `.fpk` depuis le centre d'applications ; sur OpenWrt, installez le nouveau `.ipk` / `.apk`.
- Le format de configuration est rétrocompatible. Les anciens réglages frp sont migrés en instances au premier démarrage, et les fichiers `frp/frpc.toml` et `frp/frps.toml` écrits par les anciennes versions sont supprimés.
- Les points d'accès `/api/frp/client` et `/api/frp/server` sont supprimés au profit de `/api/frp/clients`, `/api/frp/servers` et `/api/frp/settings` ; les scripts qui appellent les anciens points d'accès doivent être mis à jour.
- Le masque des mots de passe des registres Docker compte désormais 8 astérisques comme dans les autres modules ; l'ancien masque à 6 astérisques reste accepté.
